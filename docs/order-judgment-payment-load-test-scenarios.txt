주문 생성 · 공동구매 판정 · 결제 부하테스트 시나리오
작성일: 2026-09-29

1. 목적과 우선순위

사용자 혼합 트래픽과 비동기 작업이 동시에 발생하는 AWS 테스트 환경에서
주문 생성, 공동구매 판정, 결제의 처리량과 리소스 사용량을 측정한다.
최우선 합격 기준은 부하 및 장애 복구 상황에서 정합성 위반 0건이다.

우선순위:
  1) 정합성: 중복, 누락, 잘못된 상태 및 금액 반영 0건
  2) 처리량: 단위 시간당 실제 완료된 업무 건수
  3) 리소스: 애플리케이션, DB, Redis의 사용량과 경합

PG 거절이나 타임아웃 자체를 정합성 위반으로 보지는 않는다.
실패를 올바르게 기록하고, 불확실한 결과를 조회·복구해 설명 가능한 상태로
확정해야 한다. HTTP 성공률과 정합성 위반율은 별도로 집계한다.
정합성 0건은 각 테스트 실행에서 확인하는 기준이며, 모든 상황에 대한 증명은 아니다.

2. 테스트 범위와 독립 실행 구조

팀 공통: 조회, 수요 참여 등 사용자 트래픽을 합의한 비율로 계속 발생시킨다.
다른 담당자: 각자의 데이터로 수요 참여·낙찰 등 담당 시나리오를 실행한다.
본 시나리오: 별도 데이터와 실행 트리거로 공동구매 생성 이후 파이프라인을 검증한다.
같은 테스트 시간대와 백엔드·DB·Redis 자원을 공유하되, 앞 단계의 성공이나 데이터에
의존하지 않는다. 단독으로도 실행 가능하고, 팀 혼합 부하에 합쳐서도 실행 가능하게 한다.

  사용자 조회·참여 트래픽 지속
                +
  본 시나리오 전용 사전 데이터 + 공동구매 생성 트리거
    → 공동구매 생성 및 DB Outbox 기록
    → 주문 생성 요청 Stream 발행
    → Consumer가 연결 수요의 주문 생성
    → 판정 ZSET의 예정시각 도래
    → 공동구매 판정
    → 성공한 공동구매의 주문별 결제 준비 및 Outbox 기록
    → 결제 ZSET 반영
    → Payment Worker → Mock PG → DB 완료 반영

주문 Consumer, 판정 서비스, Payment Worker를 부하 도구에서 직접 호출하지 않는다.
실제 이벤트, 예약, 스케줄러를 통해 후속 작업이 수행되게 한다.
실행별 공동구매 생성 속도, 공동구매 수, 연결 수요 수, 성공·실패 판정 비율,
판정 시각은 본 시나리오에서 독립적으로 정한다.
결제는 사용자 요청 비율이 아닌 후속 업무량으로 계산한다.

2-1. 독립 데이터 준비와 시작 지점

  - 전용 회원, 활성 결제수단, 승인된 판매자, 카탈로그, 보드, 상품, 연결 수요를 준비한다.
  - 상품은 공동구매 생성 서비스가 요구하는 AWARDED 상태로 준비한다.
    연결 수요도 주문 조회 대상 상태 등 현재 서비스의 사전 조건을 충족시킨다.
  - 실제 낙찰 콜백을 실행하는 대신, 낙찰 직후에 해당하는 입력 상태를 fixture로 만든다.
    이 준비 과정은 낙찰 로직의 정확성이나 성능을 검증한 것으로 보지 않는다.
  - 주문 생성 구간과 전체 연결 검증에서는 측정 시작 후 지정한 속도로
    GroupBuyService.createGroupBuy(productId)를 호출한다.
    실제 서비스 트랜잭션이 공동구매와 Outbox를 생성하게 한다.
  - 현재 GroupBuyController에는 생성 API가 없으므로, 위 호출을 위한 테스트 전용
    내부 진입점 또는 애플리케이션 내부 실행기가 별도로 필요하다. 아직 구현된 것으로
    가정하지 않으며, 테스트 프로필에서만 활성화하고 전용 데이터만 대상으로 제한한다.
  - 생성 트리거는 상품별 한 번만 배정하고 호출 결과와 실제 생성된 공동구매를 대조한다.
    실패/응답 유실 시 무조건 재호출하지 않고 DB 상태부터 확인한다.
  - 생성 완료 상태나 주문·결제 완료 행을 SQL로 미리 넣어 본 흐름의 검증을 대체하지 않는다.

판정·결제 구간의 입력은 실제 앞 단계 서비스 경로로 사전 준비하고 검증한다.
앞 단계 준비 시간과 부하는 해당 구간의 측정에서 제외한다.
준비 단계에서 검증한 정합성과 측정 구간에서 검증한 정합성을 구분한다.

2-2. 데이터 격리와 공유 자원

  - 공통 test run ID 아래 도메인별 scenario ID 및 전용 ID 목록을 보관한다.
  - 다른 시나리오가 본 시나리오의 수요를 취소하거나 상품·보드 상태를 바꾸지 않게
    입력 데이터 풀을 분리한다. 조회 트래픽의 접근 범위는 팀에서 정한다.
  - DB·Redis·Worker는 공유한다. 본 대상의 건별 처리량·정합성과 시스템 전체 지표를
    구분해서 기록하며, 다른 도메인 데이터에서 발생한 후속 작업량도 함께 기록한다.
  - Redis 키는 실행 도중 도메인별로 임의 변경하거나 전체 삭제하지 않는다.
    같은 Stream/ZSET에 여러 시나리오 작업이 있을 수 있으므로 완료·정리 범위는
    각 manifest의 ID와 소유 관계를 기준으로 제한한다.
  - Mock 지연·장애도 본 시나리오의 주문번호/결제 ID에만 적용한다.
  - 공유 백엔드 종료는 모든 시나리오에 영향을 주므로 장애 실행은 공통 장애 구간으로
    합의해 실행하거나, 별도의 장애 실행으로 분리한다.

선택 통합 검증: 낙찰부터 결제까지 실제 연결하는 E2E 실행을 추가할 수 있다.
이 실행은 독립 시나리오와 구분해서 기록하고 같은 대상을 중복 생성하지 않는다.

2-3. 담당 구간 분리와 실행 경계

O. 주문 생성
  입력: 공동구매 생성 직전 상품과 연결 수요
  측정: 실제 공동구매 생성 → Outbox → Stream → 주문 생성 커밋 및 ACK
  종료 기준: 대상 주문 대사 완료, 해당 메시지 처리 완료
  후속 단계 제어: 판정 예정시각을 측정 종료 이후로 충분히 배치한다.

J. 판정 및 결제 예약
  입력: 주문 생성이 완료된 OPEN 공동구매와 실제 판정 예약
  측정: 판정 시각 도래 → 상태 판정 → 결제 준비·Outbox → Redis 예약 반영
  종료 기준: 예상 판정 상태 및 대상별 결제 준비·예약 반영 대사 완료
  후속 단계 제어: 결제 획득만 정지하고 예약 생성 및 Outbox Publisher는 유지한다.
  판정과 결제 예약은 현재 실행 경로상 연결되어 있어 하나의 구간으로 묶되,
  판정 처리시간과 주문별 결제 예약 생성시간은 각각 기록한다.

P. 결제 실행
  입력: 결제 준비·Outbox 발행·Redis 예약 반영이 완료된 대상
  측정: 예약 시각 도래/Worker 시작 → claim → Mock PG → DB 결과 반영 → 후속 정리
  종료 기준: 기대 최종 상태, 승인 이력 및 대상 예약 정리 대사 완료
  앞 단계 제어: 측정 대상에 대한 신규 생성·판정·예약 준비는 측정 전에 끝낸다.

데이터 분리만으로 후속 Worker의 자동 실행이 차단되지는 않는다.
J/P 준비 시 결제 획득을 제어하려면 테스트 전용 실행 제어가 필요할 수 있다.
현재 queue.enabled=false는 결제 예약 생성도 막을 수 있으므로,
이를 Worker만 멈추는 옵션으로 사용하지 않는다.
Worker만 제어하는 기능은 이미 있다고 가정하지 않으며, 구현·확인 후 사용한다.
공유 배포에서 전역 Worker를 정지하면 팀의 다른 결제에도 영향이 있으므로
독립 측정은 합의된 실행 구간 또는 전용 테스트 배포에서 수행한다.
제어할 수 없어 후속 단계도 실행된다면 '구간 단독 측정'이 아니라
'후속 부하 동반 측정'으로 표시하고 실제 실행 범위를 기록한다.

세 구간 동시 실행 시에는 O/J/P별로 데이터 풀과 manifest를 분리한다.
O의 판정은 측정 이후로 두고 P의 입력은 미리 준비한다.
J가 생성한 결제는 공유 Worker가 소비할 수 있으므로 그 후속 작업도 별도로 집계한다.
별도 제어 없이 J의 후속 결제가 멈춰 있다고 가정하지 않는다.
공유 CPU·메모리는 시스템 전체 값이며, 데이터 태그만으로 구간별 점유율을
정확히 나눌 수 없다. 구간별 실행과 동일 배경 부하의 결과를 비교해 영향을 판단한다.

3. 초기 실행 환경

  - AWS의 테스트 전용 배포 및 데이터 사용
  - Payment Worker: 인스턴스당 1개
  - 최초 기준 실행은 백엔드 인스턴스 1개로 고정하고 실제 인스턴스 수 기록
    (인스턴스가 N개이면 Worker 1 설정이어도 전체 Worker는 N개)
  - 결제 큐 활성화 여부 및 실행 구간별 Worker 획득 제어 확인
  - 결제 poll-delay: 현재 기본값 1,000ms 유지
  - Mock PG 정상 응답 지연: 300ms 고정
  - 실제 Toss 클라이언트의 base URL을 내부 Mock HTTP 서버 주소로 변경
  - Mock용 인증 키와 결제수단 데이터 사용, 실제 PG로 요청되지 않는지 사전 확인
  - 부하 발생기는 백엔드와 별도 실행 자원에 배치
  - Mock이 백엔드와 자원을 공유하면 그 구성을 기록하고 사용량을 별도 관측
  - CPU, 메모리 제한, JVM 옵션, DB 사양, Hikari 설정, Redis 구성,
    애플리케이션 버전, 인스턴스 수, 모든 폴링·재시도 설정을 실행 결과에 기록

300ms는 반복 측정을 위한 가정이며 실제 Toss 응답시간을 의미하지 않는다.
Worker 수는 처음부터 늘리지 않고, 처리량·backlog·리소스 결과를 보고 후속 실행에서 변경한다.
한 번의 비교 실행에서는 Worker 수 등 주요 변수를 하나씩 변경한다.

4. 현재 구현을 반영한 설계 조건

  - 주문 생성 이벤트는 수요마다가 아니라 공동구매당 1건 발생한다.
    이벤트 처리량과 주문 생성량은 분리해서 측정한다.
  - 주문 생성은 공동구매 단위 트랜잭션이다.
    공동구매 수와 공동구매당 수요 수를 모두 실행 조건에 기록한다.
  - 판정 예약은 상품 판매 종료시각 + 5분이다.
    테스트 중 판정되도록 판매 종료시각과 전체 실행 시간을 설계한다.
    Redis score만 앞당겨 DB의 시간 조건과 어긋나게 만들지 않는다.
  - 판정 후 주문별 결제 예약 생성이 이어진다.
    판정 완료 시각과 결제 예약 완료 시각을 분리한다.
  - PaymentWorkerPool은 폴링마다 빈 슬롯에 runOne()을 제출한다.
    Worker 1개, 폴링 1초, PG 300ms에서는 이상적인 조건에서도 대략 초당 1건 수준이다.
    1,000건은 약 17분 이상 걸릴 수 있으며, 이는 합격 SLO가 아닌 일정 산정 참고치다.
  - 결제 ZSET claim은 항목을 즉시 삭제하지 않고 score를 미래로 이동시킨다.
    ZSET 전체 크기를 미처리 결제 수로 사용하지 않는다.
  - DB Outbox, Redis Stream, ZSET을 관측한다.
    Redis LIST/LLEN 기반 Outbox 지표는 이 흐름에 적용하지 않는다.

5. 정합성 기준: 위반 허용치 0건

5-1. 주문 생성

기준: 공동구매가 생성됐을 때, 연결된 수요마다 주문이 정확히 1건 존재한다.
비동기 주문 생성 완료 기한 이후 검증한다.

  - 연결 수요의 주문 누락: 0건
  - 동일 연결 수요의 중복 주문: 0건
  - 연결되지 않은 수요의 주문 생성: 0건
  - 수요, 주문, 공동구매 간 연결 오류: 0건

주의: 현재 구현은 탈퇴 회원, 상품 가격이 희망 최고가를 초과하는 수요 등을 제외한다.
초기 데이터는 모든 연결 수요가 주문 생성 조건을 만족하도록 만든다.
연결 수요의 업무상 정의에 제외 대상까지 포함되는지는 실행 전에 팀에서 확정한다.
제외 대상을 사후에 검증 목록에서 빼서 성공으로 처리하지 않는다.

5-2. 공동구매 참여 인원과 판정

  - 참여 인원은 실제 반영 대상 주문 수와 일치한다.
    수량 합계가 아니라 현재 업무 규칙의 참여 인원 기준으로 대조한다.
  - 판정 시점 조건에 맞는 성공·실패 상태가 저장된다.
  - 중복 실행으로 인한 추가 상태 변경이나 중복 결제 예약 등 부작용은 0건이다.
  - 결제 비대상 공동구매에서 발생한 PG 승인: 0건

여러 실행자가 같은 판정 ID를 조회한 횟수 자체를 정합성 위반으로 보지 않는다.
최종 상태와 부작용의 단일 적용을 검증한다.

5-3. 결제 예약 및 실행

  - 결제 대상 주문마다 의도한 논리적 결제가 정확히 하나 존재한다.
  - 기한 이후 결제 대상 주문의 예약 누락: 0건
  - 논리적 결제별 Mock PG 실제 중복 승인: 0건
  - 주문번호, 결제 금액, 승인 식별자 매핑 오류: 0건
  - 성공 건의 주문·결제·수요 상태는 구현된 완료 규칙과 일치한다.

PG 재호출 수와 실제 승인 수는 구분한다.
재시도는 가능하지만 같은 논리적 결제에 대한 실제 승인은 한 번이어야 한다.

5-4. 복구 및 최종 대사

  - 정상 응답 시나리오에서는 모든 유효 결제 대상이 완료되어야 한다.
  - 거절 시나리오에서는 예상한 실패 상태와 승인 없음이 확인되어야 한다.
  - 승인 후 응답 유실 시나리오에서는 승인 결과 조회 후 DB가 승인 상태와 일치해야 한다.
  - 수동 확인이 예상되는 별도 조건에서는 해당 상태와 원인이 추적 가능해야 한다.
    정상 완료를 기대한 건을 수동 확인 상태라는 이유만으로 합격시키지 않는다.
  - 복구 기한 이후 원인이 설명되지 않는 미처리·누락·상태 불일치: 0건

실행 중 항상 금지: 중복 승인, 잘못된 금액 청구, 잘못된 상태 전이.
기한 내 해소: 처리 대기, 재시도 대기, PG 승인과 DB 반영 사이의 일시적 차이.
금지된 중간 상태나 부작용은 최종 상태만으로 놓칠 수 있어 전이·승인 이력도 확인한다.

6. 검증 데이터와 대사 방법

실행 전 공통 run ID, 본 scenario ID와 예상 대상 목록(manifest)을 별도 보관한다.
manifest에는 보드, 연결 수요, 예상 주문 대상, 예상 판정 결과,
예상 결제 대상과 금액, 판정 예정시각, 주입할 장애 및 예상 최종 상태를 기록한다.
주문·결제 ID는 생성 후 원본 수요와 공동구매 ID를 통해 연결한다.

검증 연결:
  연결 수요 ID → 주문 ID → 결제 ID/주문번호 → Mock PG 승인 이력

  - 총건수뿐 아니라 각 ID별 존재 여부 및 개수를 비교한다.
  - 한 건 누락과 다른 한 건 중복이 총건수에서 상쇄되지 않게 한다.
  - 최종 대사 대상은 DB에 생성된 행 목록이 아니라 사전에 확보한 예상 대상 목록이다.
  - 처리 중에는 샘플링·집계 관측을 사용하고, 종료 후 대상 전체를 대사한다.
  - 검증 쿼리의 실행 주기와 비용을 기록해 측정 부하에 미치는 영향을 관리한다.
  - 실패 ID, 기대값, 실제값, 관련 승인·전이 이력을 결과에 보존한다.

7. 측정 지표

7-1. 처리량
  - 커밋된 신규 주문 수/초
  - 실제 판정 완료 공동구매 수/초
  - 신규 결제 준비·예약 완료 수/초
  - DB 결제 성공 완료 수/초
  - 확정 실패·수동 확인 전환 수/초: 성공 처리량과 별도 집계
  - PG 요청·재시도·조회 수/초와 실제 신규 승인 수/초

7-2. 대기와 완료 시간
  - Outbox 유형별 미발행 수, 현재 미발행 상태의 최장 대기시간
  - 주문 Stream consumer group lag 및 pending
  - 판정 ZSET due 수와 예정시각 대비 판정 지연
  - 판정 완료부터 결제 예약 완료까지의 시간
  - 결제 ZSET due 수, DB 처리 중·재시도 대기 수
  - 최초 실행 예정시각부터 결제 완료까지 p95/p99 및 최대값
  - 신규 유입 종료부터 잔여 대상 처리 완료까지의 시간

결제 claim·재시도로 Redis score가 바뀌므로 최초 예정시각은 별도로 보관한다.
due 수가 0이어도 처리 중·미발행·미예약 작업이 남을 수 있으므로 완료로 단정하지 않는다.
결제 Outbox는 기존 행이 다시 미발행으로 전환될 수 있어 INSERT 수만으로 유입량을 판단하지 않는다.

7-3. 리소스
  - 애플리케이션 프로세스/컨테이너 CPU, 메모리, heap, GC pause, 스레드
  - 결제 Worker 실행 중 개수와 점유 시간
  - Hikari active, idle, pending, 커넥션 획득 시간
  - PostgreSQL CPU, 메모리, I/O, 쿼리 지연, 트랜잭션 시간, 락 대기
  - Redis CPU, 메모리, 명령 지연
  - Mock PG와 부하 발생기 CPU·메모리 및 목표 부하 달성 여부

CPU가 낮아도 PG 대기나 폴링으로 처리량이 제한될 수 있다.
Worker 증설 판단에는 backlog 증가율과 완료 지연을 함께 사용한다.

8. 실행 시나리오와 순서

공통: 통합 실행에서는 팀 사용자 혼합 트래픽을 유지하고 API별 응답시간·오류율도 관측한다.
각 실행은 본 담당자가 새로 준비한 격리 데이터와 독립 트리거로 시작한다.
팀의 낙찰 시나리오 완료를 기다리지 않는다. 단독 실행 시에는 배경 트래픽이 없음을 기록한다.
아래 규모는 시작 예시이며 운영 피크 추정치가 아니다.

진행 순서:
  A. O/J/P 구간별 기준 측정 및 부하 증가
    → B. 세 구간 동시 부하
    → C. 작은 규모의 전체 연결 검증
    → D~F. 지연·장애 복구 검증

A. 구간별 기준 측정 및 부하 증가
  - O/J/P를 서로 다른 실행으로 측정하고 팀 배경 트래픽 조건은 동일하게 유지한다.
  - O: 10개 공동구매 × 연결 수요 10건부터 시작하여 주문 100건 대사
  - J: 주문 준비를 마친 공동구매 10개부터 시작하여 판정·결제 예약 대사
       성공·실패 판정용 대상을 구분하고 공동구매 수와 주문 수를 모두 기록
  - P: 준비된 결제 100건, Worker 1개, Mock 300ms로 완료 및 승인 이력 대사
  - 각 구간에서 대상 1,000건 이상으로 확대하되 단위를 명시한다.
    예: O는 주문 수, J는 공동구매 수 및 결제 예약 대상 수, P는 결제 수
  - O/J는 100개 × 10건과 10개 × 100건처럼 공동구매당 작업 크기도 비교한다.
  - J는 판정 시각 분산/집중, P는 결제 시각 분산/집중을 별도 실행으로 비교한다.
  - 목표: 구간별 처리량·리소스·경합·정합성 확보
  - 각 구간 종료 경계까지만 합격 판정하며 실행하지 않은 후속 구간은 미검증으로 표시

B. 세 구간 동시 부하
  - O용 생성 직전 데이터, J용 주문 완료 데이터, P용 결제 예약 완료 데이터를 별도로 준비
  - 같은 측정 시간대에 O 생성 요청, J 판정 도래, P 결제 도래를 함께 발생
  - 각 구간은 우선 대상 주문/결제 100건 수준으로 시작하고 개별 입력량을 기록
  - 이후 특정 구간만 증량하여 다른 구간 처리량·지연·정합성에 미치는 영향 비교
  - J가 발생시키는 후속 결제는 J 출처로 분류해 P의 사전 준비 데이터와 구분
  - 공유 Worker의 전체 처리량에는 P 대상과 J 후속 결제를 모두 포함
  - 목표: 주문 INSERT, 판정·예약, 결제 반영이 공유 자원에서 경합할 때 정합성 0건
  - 본 담당 데이터 전체에 대한 대사는 각 출처별 및 합산 결과를 함께 기록

C. 전체 연결 검증
  - 생성 직전부터 시작하는 별도 데이터로 실제 주문 → 판정 → 결제 전체 실행
  - 성공 공동구매 10개 × 연결 수요 10건 = 주문·결제 대상 100건부터 시작
  - 실패 판정용 공동구매도 별도 준비해 결제 비발생 확인
  - Worker 1개, Mock 300ms, 후속 단계 제어 없이 실제 파이프라인 실행
  - 목표: 구간 간 전달 누락, 트랜잭션 경계, 전체 데이터 연결과 최종 정합성 검증
  - 주문 완료 후 집중 마감 실행도 추가해 전체 backlog 및 해소 시간 측정
  - API 부하 종료 후에도 전체 대상 완료까지 관측

D. 외부 응답 지연
  - P 구간의 작은 규모에서 시작하고 C 연결 검증에서도 확인, 매번 새 데이터 사용
  - Mock PG 응답을 3초 고정으로 변경
  - 목표: Worker 점유, 처리량 감소, 커넥션 사용, 사용자 API 영향 확인
  - 지연 자체로 타임아웃을 기대하지 않는다. 현재 읽기 타임아웃은 5초이다.

E. 승인 후 응답 유실
  - P 구간에서 재현 후 C 연결 검증에 같은 조건 적용
  - 대상 100건 중 미리 지정한 5건의 첫 승인 응답을 7초 지연
  - Mock은 요청을 승인 이력에 기록한 뒤 응답을 지연한다.
  - 승인 조회 API는 해당 승인 결과를 정상 반환한다.
  - 나머지 요청과 후속 조회는 기본 300ms 응답
  - 목표: 타임아웃 후 기존 승인 조회, DB 완료 반영, 실제 중복 승인 0건
  - 재시도/조회 완료와 관련 Outbox 정리까지 관측

F. 처리 중 종료·재시작
  - P 구간에서 복구 경로 확인 후 C 연결 검증에서 최종 연결 상태도 확인
  - 테스트 전용 프로세스에서 수행, 대상은 우선 100건
  - 별도 실행으로 아래 지점을 재현하고 실제 종료 시점을 증거로 기록
    1) Redis claim 이후 DB 실행 상태 확보 전
    2) PG 승인 이후 DB 완료 커밋 전
    3) DB 완료 커밋 이후 Redis 정리 전
  - 종료 위치를 재현할 테스트 장치가 없으면 임의 종료 결과와 구분해 미검증으로 기록
  - 강제 종료 후 재시작하고 visibility/lease, 폴링, 재시도 시간을 포함해 관측
  - 목표: 미완료 작업 복구, 중복 승인 0건, 누락 0건
  - 정상 종료 대기 후 재시작은 강제 종료 테스트를 대체하지 않는다.

선택 확장:
  - 여러 백엔드 인스턴스가 같은 Redis·DB를 사용하는 동시 실행 검증
  - 각 인스턴스 Worker는 1개로 유지하고 전체 실행자 수를 명시
  - 단일 인스턴스 결과만으로 다중 인스턴스 정합성을 검증했다고 표현하지 않는다.

9. 실행 절차

  1) 구간별/동시/연결 실행 유형과 팀 배경 부하, 각 구간 입력 속도·데이터 수 확정
  2) 정상 완료 기한과 장애 복구 기한을 실행 전에 기록
  3) O/J/P 또는 연결 검증용 fixture, manifest, Mock 상태와 모니터링 준비
  4) 시작 상태, 구간 경계 제어, 실제 Mock 연결과 이벤트 흐름을 소규모 검증
  5) 짧은 워밍업 후 측정 구간 시작
  6) 팀 사용자 트래픽과 선택 구간의 생성 트리거/판정 도래/결제 도래를 함께 실행
  7) 해당 시나리오의 마감 집중 또는 지연·장애 조건 적용
  8) 신규 유입 종료, 비동기 작업은 계속 처리하며 관측
  9) 완료 기한 도래 또는 대상 처리 완료 후 선택한 구간 경계까지 전체 대상 대사
 10) 결과·실패 ID·Mock 승인 이력·설정·그래프 저장
 11) 대상 작업의 처리 종료를 확인하고 본 manifest에 속한 데이터만 정리
     공유 Worker 중지나 공용 DB·Redis 전체 리셋은 팀 전체 실행 종료 후 공동 절차로 수행

기한을 사후에 늘려 미완료 작업을 숨기지 않는다.
사전에 정한 기한을 초과하면 실패로 남기고, 추가 복구 관측은 별도로 기록한다.
아직 팀 SLO가 없으면 기준 실행은 성능 탐색으로 표시하며 정합성 결과와 구분한다.

10. Mock PG 요구사항

  - 현재 Toss 클라이언트가 호출하는 결제 및 주문번호 조회 경로 지원
  - 주문번호, 금액, 승인 시각 등 클라이언트 검증을 통과하는 응답
  - 멱등키별 승인 결과 저장 및 동일 요청 재호출 시 결과 재사용
  - 실제 신규 승인 횟수와 API 호출 횟수 별도 기록
  - 요청 ID/주문번호별 고정 지연 및 승인 후 응답 지연 주입
  - 애플리케이션 재시작 동안 Mock 승인 이력 유지
  - 대사 완료 전 이력을 초기화하지 않음

11. 합격 판정 및 결과 보고

필수 합격 조건 (실행한 구간에 적용):
  - 주문 누락·중복·잘못된 연결: 각각 0건
  - 참여 인원·판정 상태 오류: 0건
  - 결제 예약 누락·중복 논리 결제: 0건
  - Mock PG 실제 중복 승인·잘못된 금액 승인: 0건
  - 완료/복구 기한 이후 예상 결과와 불일치: 0건
  - 부하 발생기가 목표 부하를 달성했는지 확인

O 단독 실행은 주문·참여 인원, J는 판정·결제 예약, P는 결제 실행·복구를 판정한다.
구간 밖의 결과는 통과가 아니라 미검증으로 기록한다.
동시 실행은 각 데이터 풀의 실행 범위와 J 후속 결제를 포함해 검증하고,
C 전체 연결 검증에서는 위 기준 모두를 적용한다.

목표 부하를 발생시키지 못했다면 그 부하를 통과했다고 보고하지 않는다.
처리량이나 리소스 수치가 좋아도 정합성 위반이 하나라도 있으면 실패이다.
리소스 사용률은 관측값과 실행 전 정한 한도를 비교하며 임의의 공통 한도를 가정하지 않는다.

결과 기록 양식:
  - 공통 run ID / scenario ID / 단독·통합 실행 여부 / 버전 / 인프라 사양 / 인스턴스 수
  - O/J/P 구간 / 구간별·동시·연결 실행 유형 / 입력 상태 / 측정 종료 경계
  - 후속 단계 제어 방식 / 준비 단계 제외 범위 / 실제 후속 작업 발생량
  - Worker 수 / 폴링 간격 / Mock 조건
  - 배경 사용자 RPS / 본 공동구매 생성 목표·실제 속도 / 판정 대상 유입률
  - 다른 시나리오에서 유입된 주문·결제 등 공유 파이프라인 작업량
  - 공동구매 수 / 연결 수요 수 / 예상 주문·결제 대상 수
  - 주문·판정·결제 완료 처리량: 구간 평균과 시계열
  - backlog 최대값 / 유입 종료 후 해소 시간
  - 결제 완료 지연 p95·p99 / 최장 지연
  - CPU·메모리·Hikari pending·DB 락·Redis 지연
  - 정합성 위반 유형별 건수와 실패 ID
  - 기한 초과 건수 / 미검증 항목 / 최종 합격 여부
