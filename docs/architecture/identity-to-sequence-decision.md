# IDENTITY → SEQUENCE 전환 결정 기록

## 요약

`ProductAwardEvaluation`만 SEQUENCE 로 전환. 나머지 20개 IDENTITY 엔티티는 유지.

| 엔티티                                                | 결정            | 판단 근거                                 |
|----------------------------------------------------|---------------|---------------------------------------|
| `ProductAwardEvaluation`                           | ✅ SEQUENCE 전환 | Bulk INSERT 大, FK 없음, 코드 변경 없음        |
| `DemandBoard`                                      | ❌ IDENTITY 유지 | Bulk INSERT 있지만 FK 종속으로 이득 감소, 복잡도 상승 |
| 나머지 18개 (Member, Product, GroupBuy, OutboxEvent 등) | ❌ IDENTITY 유지 | 대부분 단건 INSERT, batch 필요성 없음           |

---

## 배경: IDENTITY 는 왜 batch INSERT 를 못 하는가

### PostgreSQL 관점

두 방식 모두 auto-increment 이지만 **ID 발급 타이밍이 다름**:

- **IDENTITY** (`GENERATED BY DEFAULT AS IDENTITY`): INSERT 실행 도중에 DB 가 ID 발급
- **SEQUENCE** (`DEFAULT nextval('seq')`): 명시적 sequence 객체에서 미리 ID 발급 가능

두 방식 모두 내부적으로 sequence 를 사용하지만, IDENTITY 는 sequence 를 숨김 처리해서 INSERT 문 실행 전에 ID 를 조회할 방법이 없음.

### Hibernate 관점

**IDENTITY 엔티티의 `persist()` / `save()`:**

- Hibernate 가 `EntityIdentityInsertAction` 이라는 **즉시 실행 액션** 을 생성
- persist() 가 return 하기 전에 **반드시 INSERT 를 실행**해서 ID 를 받아옴
- 이유: 영속성 컨텍스트가 엔티티를 "identity" 로 관리하려면 ID 가 필요
- **배치 불가능**: 각 INSERT 가 독립 왕복

**SEQUENCE 엔티티의 `persist()` / `save()`:**

- sequence 에서 미리 ID 를 받아 엔티티에 세팅 (cache 활용 시 매번 왕복 없음)
- INSERT 는 flush 시점까지 지연
- Flush 시점에 `hibernate.jdbc.batch_size` 크기만큼 **묶어서 batch 로 전송**

### 성능 비교

Chunk 10개 board × board 당 evaluation 5개 = 50개 INSERT 시나리오:

| 방식                       | Round trips                              |
|--------------------------|------------------------------------------|
| IDENTITY                 | 50 (각 INSERT 마다 개별 왕복)                   |
| SEQUENCE + batch_size=20 | 1~2 (batch 로 묶임) + 1 (sequence 초기 fetch) |

**~48 RTT 절약.**

## 전환 결정 상세

### ✅ ProductAwardEvaluation — SEQUENCE 로 전환

**이유:**

## 현재 내용에도 왜 이를 도입했는가 (batch flush를 적용한 특별한 이유, flush 를 하나씩만 적용하면 안됐나?

)

1. **Bulk INSERT 규모가 큼**
    - `award(BoardResult)` 안에서
      `productAwardEvaluationRepository.saveAll(fromBoardResult(boardResult))` 호출
    - Board 당 후보 상품 수만큼 evaluation INSERT (보통 2~10개)
    - `awardChunk` 는 10개 board 를 처리 → chunk 당 20~100개 evaluation

2. **FK 종속 없음**
    - 저장 후 다른 native query 가 이 테이블의 새 row 를 참조하지 않음
    - `saveAll` 반환값도 사용하지 않음 (ID fetch 불필요)
    - 커밋 시점까지 INSERT 를 완전히 지연 가능 → batching 이득 100% 활용

3. **코드 변경 없음**
    - `saveAll(entities)` API 는 그대로 유지
    - 어노테이션과 스키마만 변경

4. **마이그레이션 리스크 낮음**
    - 참조 관계 단순
    - 기존 ID 는 그대로 보존 (sequence 를 `MAX(id)` 로 초기화)

**적용 내역:**

- `V13__product_award_evaluation_sequence.sql`: sequence 생성, 컬럼 default 변경, setval 초기화
- `ProductAwardEvaluation.java`: `@GeneratedValue(SEQUENCE)` +
  `@SequenceGenerator(allocationSize = 20)`
- `application.yml`: 기존 `jdbc.batch_size: 20`, `order_inserts: true` 재사용

**예상 이득:**

- Award chunk 당 RTT 50 → 2 (~48 절약)
- Award 트래픽이 증가하면 실질 병목 해소

### ❌ DemandBoard — IDENTITY 유지

**전환하지 않은 이유:**

1. **FK 종속으로 인한 batching 이득 감소**

   `createNewBoardChunk` 흐름:
   ```java
   List<DemandBoard> savedList = newBoards.stream()
       .map(newBoard -> demandBoardRepository.save(newBoard.toEntity()))
       .toList();

   for (int i = 0; i < savedList.size(); i++) {
       demandRepository.assignToBoard(
           savedList.get(i).getId(),  // ← 방금 발급받은 board id
           ...
           newBoards.get(i).demandIds());  // ← demand.demand_board_id 로 FK
   }
   ```

    - `assignToBoard` 는 `demand.demand_board_id` 를 방금 생성한 board id 로 UPDATE
    - **FK 제약** 때문에 board 가 DB 에 실제로 INSERT 되어 있어야 UPDATE 성공
    - SEQUENCE 로 전환 시 명시적 `entityManager.flush()` 를 save loop 후에 강제로 넣어야 안전
    - "커밋까지 지연" 이라는 장점 상실

2. **Batching 이득은 남지만 상대적으로 작음**

   Chunk 10개 board 기준:
    - IDENTITY: 10 INSERT × 1 RTT = 10 RTT
    - SEQUENCE + explicit flush: 1~2 RTT (batch)
    - **절약: ~8 RTT**

   ProductAwardEvaluation 의 ~48 RTT 절약과 비교하면 상대적으로 미미.

3. **코드 복잡도 상승**
    - 명시적 `entityManager.flush()` 추가 필요 (FK 안전성 확보)
    - 팀원이 이 flush 의 존재 이유를 이해해야 함
    - 미래 리팩토링 시 실수로 제거될 위험

4. **트래픽 특성**
    - Formation-plan 배치는 award 만큼 자주 실행되지 않음
    - 절약 RTT 가 크지 않으면 프로파일링에서도 병목으로 드러나지 않음
    - 지금 시점 최적화 우선순위 낮음

5. **마이그레이션 리스크**
    - `demand_board.id` 는 `demand.demand_board_id`, `product.demand_board_id`,
      `product_award_evaluation.demand_board_id`, `reject_history.demand_board_id` 등 여러 곳에서 참조
    - IDENTITY 컬럼 변경 자체는 참조하는 컬럼에 영향 없지만, 넓은 참조 관계는 신중한 검토 필요

**결론:** 이득이 명확하지 않은 상태에서 복잡도만 늘리는 마이그레이션은 미룸. 프로파일링에서 이 경로가 병목으로 확인되면 그때 재검토.

### ❌ 나머지 18개 IDENTITY 엔티티 — 유지

**해당 엔티티들:**
`Member`, `Seller`, `LocalCredential`, `SocialCredential`, `ShippingAddress`, `Product`,
`ProductCatalog`, `GroupBuy`, `Payments`, `PaymentsWebhook`, `BrandPayMethod`, `Payout`,
`SellerPayoutAccount`, `OutboxEvent`, `Notification`, `NotificationEvent`, `Category`, `Demand`

**공통 이유: 단건 INSERT 패턴**

이들 엔티티는 대부분 다음 형태로 사용됨:

```java
repository.save(entity);
```

- 회원가입, 결제, 알림 등 개별 이벤트 처리
- Bulk save 없음 → batching 이 아예 불가능
- SEQUENCE 로 바꿔도 얻는 이득 없음

**Demand 예외 확인:** `join` 에서 `demandRepository.saveAndFlush(demand)` 단건. Bulk 없음.

**참고 — 이미 SEQUENCE 인 엔티티: `Orders`**

- `OrderService` 의 batch order 생성 로직에서 이미 이득을 얻고 있음
- 이 프로젝트에서 SEQUENCE 사용 선례로 참고 가능

## Trade-off 정리

### SEQUENCE 의 장점

- Batch INSERT 가능 → 대량 INSERT 시 RTT 대폭 감소
- Hibernate 가 flush 시점을 유연하게 관리 (지연 가능)

### SEQUENCE 의 단점

- **ID gap 발생**: `allocationSize` 만큼 미리 예약 → 서비스 재시작 시 미사용분 소진 (예: 20개 예약 후 5개만 쓰고 재시작 → 15개 gap)
- **PostgreSQL 전용**: MySQL 은 SEQUENCE 미지원 → 이전 시 재검토
- **명시적 sequence 관리 필요**: Flyway 마이그레이션 추가, 스키마 복잡도 미세 증가
- **마이그레이션 리스크**: `ALTER COLUMN ... DROP IDENTITY` 는 짧지만 DDL 락 필요

### IDENTITY 의 장점

- 스키마 간결 (컬럼 정의에 포함)
- ID gap 최소화 (INSERT 실패 시에만 gap)
- 이식성 (MySQL 등 다른 DB 로 이전 시 호환)

### IDENTITY 의 단점

- **Batch INSERT 불가능** — Hibernate 가 즉시 실행 강제
- 대량 INSERT 시 RTT 낭비

## 언제 SEQUENCE 로 전환할지 (미래 판단 기준)

새 엔티티나 기존 엔티티 재검토 시 아래 체크리스트로 판단:

- [ ] **Bulk INSERT 가 실제로 일어나는가?** (`saveAll` 또는 loop `save`)
- [ ] **한 번에 저장하는 개수가 5개 이상인가?** (batch 효과가 유의미해지는 하한)
- [ ] **저장 후 즉시 native query 가 이 테이블의 새 row 를 참조하는가?** (No 여야 이득 최대)
- [ ] **saveAll 반환값의 ID 를 사용하는가?** (No 여야 이득 최대)
- [ ] **트래픽 규모가 유의미한가?** (배치가 자주 돌지 않으면 우선순위 낮음)

**전부 Yes → SEQUENCE 전환 강한 후보**
**한둘 No → 재검토 필요**
