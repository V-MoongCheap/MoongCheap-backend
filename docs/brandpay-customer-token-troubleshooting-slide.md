# 추가 리다이렉트가 로컬 서버의 OPTIONS 501을 유발해 결제수단 등록이 실패하고 있었다

> 발표용 1장 구성 · BrandPay 결제수단 등록 · 발표 시간 40~60초
> 근거: [원본 트러블슈팅 기록](./brandpay-customer-token-troubleshooting.md)

## 장표에 넣을 내용

### 왼쪽 — 증상 → 원인 추적 → 해결

**① 증상·영향 | 결제수단 등록 화면**  
카드·계좌 등록 시 “customerToken이 존재하지 않습니다” 오류 발생. 결제 준비 단계인 결제수단 등록이 막혀, 등록한 수단으로 결제하는 시연 동선을 진행할 수 없었다.

↓

**② 가설 검증 | 세션·설정 → DB 확인**  
처음에는 세션 누락이나 인증 설정 문제를 의심했다. 실제 회원 세션으로 콜백이 처리됐고 리다이렉트 URL도 일치했다. DB에는 Access/Refresh Token이 저장돼 있어, 해당 요청의 토큰 발급 이후 구간으로 추적 범위를 좁혔다.

↓

**③ 원인 확인 | 브라우저 네트워크·SDK 로그 대조**  
콜백의 `302` 응답 뒤 프론트 정적 서버에서 `OPTIONS 501`이 발생했다. 같은 시각·Trace ID의 SDK 로그에서도 `Redirect url failed`가 토큰 오류보다 먼저 나타났다. 화면의 토큰 오류는 후속 증상이었고, 실제 원인은 **백엔드의 추가 리다이렉트와 이를 받는 로컬 정적 서버의 요청 처리 한계**였다.

↓

**④ 해결·판단 | 콜백 응답 302 → 204**  
토큰 발급·동기화 후 콜백을 `204 No Content`로 종료하고, 프론트의 불필요한 성공 URL 처리를 제거했다. 정적 서버에 OPTIONS 지원을 추가하는 대신 추가 이동 자체를 없앴다. 기존 화면의 SDK 작업이 이어질 수 있어, 교차 출처 요청과 로컬 서버 설정에 대한 의존성을 줄이는 방법이었다.

### 오른쪽 — 증거 캡처 1장

**[캡처 삽입 위치 — 원본 문서에는 실제 이미지가 없어 별도 확보 필요]**

브라우저 개발자도구의 Network 화면에서 아래 두 요청이 이어지는 부분을 한 장으로 캡처한다. 기존 캡처가 없다면 수정 전 환경에서 재현한 자료임을 표기한다.

```text
GET     localhost:8080/api/dev/brandpay-test/callback → 302
OPTIONS localhost:3000/?brandpay=success             → 501
```

캡처 설명: **“토큰 발급 후 추가 이동에서 실패했다.”**

URL 쿼리의 `code`·`customerKey`, 쿠키 및 토큰 값은 가린다. 장표에는 두 요청과 상태 코드만 강조한다.

### 하단 — 결과 숫자·시연 연결

**카드·계좌 2종 등록 성공 확인 · 콜백 최종 응답 302 → 204**  
백엔드 재시작 후 등록 성공을 확인했다. SDK 완료 뒤 결제수단 동기화·목록 조회로 이어지는 흐름을 원본 기록에 정리했다.

“시연에서 결제수단을 등록할 때, 뒤에서는 인증 콜백이 204로 끝나고 SDK가 등록을 이어가는 흐름이 동작합니다.”

## 발표 대본 — 40~60초 목표

“방금 보신 결제수단 등록은, 인증 콜백이 204로 끝나면서 SDK가 등록을 이어가는 흐름입니다. 처음에는 카드와 계좌 모두 customerToken이 없다는 오류로 등록이 막혔습니다.

세션이나 인증 설정을 의심했지만, 실제 회원 세션으로 콜백이 처리됐고 DB에도 토큰이 저장돼 있었습니다. 브라우저 요청과 같은 시각의 SDK 로그를 대조하니, 토큰 발급 뒤 추가 리다이렉트가 로컬 서버의 OPTIONS 501을 만나 실패했고, 토큰 오류는 그다음에 나타난 증상이었습니다.

그래서 추가 이동을 없애고 콜백을 204로 종료했습니다. 로컬 서버 설정에 대한 의존성을 줄이면서 기존 SDK 흐름을 이어갈 수 있었고, 재시작 후 카드와 계좌 두 종류 모두 등록에 성공했습니다.”

## 발표 전 확인 사항 — 장표에는 제외

- 위 결과는 원본 문서에 기록된 검증 결과다. 이 발표 자료 작성 과정에서 기능 테스트를 새로 실행한 것은 아니다.
- ‘2종’은 카드·계좌라는 결제수단 유형 수다. 테스트 케이스 2건 또는 전체 결제 시나리오 검증 완료를 뜻하지 않는다.
- 발견·해결 시각, 소요 시간, 재발 관찰 기간·횟수는 원본에 없다. 추가 기록 없이 ‘○시간 만에 해결’, ‘재발 0회’로 표기하지 않는다. 추적 흐름에도 임의의 시각을 넣지 않았다.
- 발견자·추적자·해결자 정보는 원본에 없다. 공동 사례로 발표한다면 확인된 역할과 시각만 추가한다.
- 실제 증거 캡처 1장을 삽입하고, 시연에서도 해당 흐름을 사용하는지 확인한 뒤 시연 연결 문장을 사용한다.
