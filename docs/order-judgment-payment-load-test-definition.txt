# 부하 테스트 시나리오 — 주문 생성 · 결제

부하 상황에서 **정합성 위반 0건**을 유지하는지 확인하고, 처리량과 리소스 점유율을 측정하는 정의서.
팀의 다른 도메인과 같은 시간에 같은 시스템에서 실행하되, 데이터와 시작 조건은 독립적으로 준비한다.
상세 기준 문서: docs/order-judgment-payment-load-test-scenarios.txt
이번 실행 범위는 시간 제약에 따라 본 정의서의 축소 계획을 우선한다.
P(결제)를 우선 실행하고, 시간이 허용되면 O(주문 생성)를 추가한다.

---

## 공통 사항

### 도구
- **부하 발생**: k6 (HTTP 진입점이 필요한 구간), 예약 데이터 및 실제 스케줄러/Worker
- **관측**: Grafana + Prometheus + PostgreSQL 활동/락 지표 + Redis Stream/ZSET 지표
- **검증**: 실행 전 예상 대상 manifest + DB 건별 대사 + Mock PG 승인 이력
- **오케스트레이션**: Makefile / shell / 테스트 전용 내부 실행기
- 본 문서의 fixture·실행기·검증 스크립트는 구현할 구성 요소이다. 이미 존재하는 것으로 가정하지 않는다.

### 초기 조건
| 항목 | 설정 |
|------|------|
| 환경 | AWS 테스트 전용 배포 및 데이터 |
| 백엔드 인스턴스 | 최초 기준 실행은 1개, 실제 수 기록 |
| Payment Worker | 인스턴스당 1개 |
| 결제 polling | 1,000ms |
| 가상 결제 | 앱 내부 테스트 구현체에서 300ms sleep 후 정상 응답 |
| 결제 구현 선택 | 배포 시 설정으로 실제 Toss / 가상 결제 구현체 선택 |
| 배경 부하 | 팀 조회·수요 참여 등 혼합 트래픽, 구간별 비교 시 동일 조건 유지 |

300ms는 반복 측정용 가정이며 실제 Toss 응답시간을 의미하지 않는다.
다중 인스턴스에서는 전체 Worker 수가 증가하므로 인스턴스 수를 반드시 기록한다.
부하 발생기는 백엔드와 별도 자원을 사용한다. 가상 결제는 백엔드 프로세스 안에서 실행된다.

### 배포 및 QA 복귀 방식
- 결제 모드·지연시간·Worker 획득 활성 여부는 배포 시 설정하고 변경 시 재배포한다.
- 동적 Redis/DB 설정이나 런타임 모드 변경 API는 구현하지 않는다.
- 테스트 구현체와 지원 기능은 전용 설정에서만 활성화하며 기본값은 비활성화한다.
- 실제 Toss와 가상 결제 중 하나가 명확히 선택되게 구성하고 실제 적용 모드를 확인한다.
- 별도 Mock HTTP 서버를 추가하지 않고 BrandPayPaymentClient와 승인 조회의 테스트 구현체를 사용한다.
- QA와 부하테스트 시간을 조율하고 실행 중 QA 조작은 중지한다.
- Worker만 중지하는 별도 시작 설정을 준비한다. queue.enabled=false로 예약 생성까지 막지 않는다.
- P 준비 시 Worker 획득을 끈 설정으로 데이터를 준비하고, 가상 결제 모드를 유지한 채
  Worker 획득을 켜서 재배포한다. 시작 직후 처리될 수 있으므로 모니터링을 먼저 시작한다.
- 재배포 준비 시간과 앱 기동 시간은 결제 처리량 측정 구간과 구분한다.
- QA 복귀 전 신규 테스트 유입 중지 → 진행 중 작업 완료 및 대사 → 결과 보존
  → 테스트 잔여 예약·재시도·복구 대상 정리 → QA 설정으로 재배포 순서로 진행한다.
- 테스트 결제 DB 상태나 Outbox에서 예약이 복원될 수 있으므로 Redis 항목만 지우지 않는다.
  실제 Toss 모드로 복귀하기 전에 실행 가능한 테스트 결제가 남지 않았음을 확인한다.
- 승인 이력이 메모리라면 재배포 전에 대사·이력 보존을 마친다.

### 구현된 배포 설정
| 환경변수 | 기본값 | 의미 |
|----------|--------|------|
| PAYMENT_GATEWAY_MODE | toss | toss 또는 mock, 잘못된 값은 기동 실패 |
| PAYMENT_MOCK_DELAY | 300ms | 가상 결제 및 승인 조회 지연, 0~30초 |
| PAYMENT_QUEUE_ENABLED | false | 기존 결제 큐·예약 처리 활성 설정 |
| PAYMENT_WORKER_ENABLED | true | 큐 활성 상태에서 Worker의 신규 획득 허용 |

부하테스트 데이터 준비 배포:
```text
PAYMENT_GATEWAY_MODE=mock
PAYMENT_MOCK_DELAY=300ms
PAYMENT_QUEUE_ENABLED=true
PAYMENT_WORKER_ENABLED=false
```
결제 측정 배포: 위 설정에서 PAYMENT_WORKER_ENABLED=true로 변경한다.
QA 복귀: 테스트 대사·잔여 작업 정리 후 PAYMENT_GATEWAY_MODE=toss로 변경하고,
QUEUE_ENABLED와 WORKER_ENABLED는 기존 QA 설정으로 복원한다.
환경변수는 실제 백엔드 프로세스/컨테이너에 전달해야 한다.

현재 구현 범위:
- 결제·승인 조회 가상 구현, 멱등키/주문번호 일치 검사, 메모리 승인 스냅샷 및 호출 수 제공.
- 가상 결제 취소는 명시적 미지원 오류를 반환하며 실제 Toss로 전달하지 않는다.
- 결제수단 등록·인증·토큰 관련 Toss 클라이언트는 교체하지 않는다. fixture를 사전 준비한다.
- 메모리 승인은 인스턴스별로 보관되므로 이 구현의 테스트는 단일 인스턴스로 제한한다.
- 승인 조회/스냅샷 메서드는 내부 코드용이며 외부 다운로드 API는 아직 없다.
- O 데이터 시딩·생성·대사 API와 k6 실행 스크립트는 tools/load-test/README.md 참고.
- LOAD_TEST_ENABLED=true로 활성화하며 내부 API 키, mock 모드, Worker 획득 중지가 필요하다.
- 장애 주입과 P 전용 시딩·대사는 후속 구현 대상이다.

### 성공 기준
- **정합성 위반: 0건** — 중복, 누락, 잘못된 연결·상태·금액.
- 실행한 구간의 모든 대상을 사전에 정한 완료/복구 기한 안에 대사한다.
- 목표 유입량을 실제로 발생시켰는지 확인한다. 미달하면 목표 부하 통과로 보고하지 않는다.
- 처리량과 리소스는 시계열로 기록하고, 팀이 정한 용량·완료 기한과 비교한다.
- PG 거절·타임아웃 수와 정합성 위반 수는 별도 집계한다.
- 정상 응답 시나리오는 모든 유효 대상의 정상 완료가 필요하다.
- 장애 시나리오는 사전에 정한 기대 결과와 일치해야 한다. 수동 확인 상태를 무조건 성공으로 간주하지 않는다.

완료/복구 기한과 운영 목표 부하는 실행 전에 확정한다.
아직 SLO가 없으면 성능 탐색 실행으로 표시하고 정합성 결과와 구분한다.

### 시딩 및 데이터 격리 원칙
- 공통 run ID 아래 실제 선택한 O(주문), P(결제)의 manifest만 만든다.
- 전용 회원·결제수단·판매자·카탈로그·보드·상품·수요를 사용한다.
- 다른 팀 시나리오가 이 데이터를 수정하지 않게 입력 풀을 분리한다.
- FK, unique 제약과 실제 서비스의 상태·가격·회원·결제수단 조건을 만족한다.
- 준비 데이터의 규모, 준비 완료 시각, 측정에서 제외한 범위를 기록한다.
- DB/Redis/Worker는 공유하므로 전체 리소스와 본 대상 처리량을 구분한다.
- 종료 시 manifest에 속한 데이터만 정리하며 공용 Stream/ZSET을 통째로 삭제하지 않는다.

### 이번 실행 범위와 우선순위
| 가능한 구간 수 | 권장 선택 | 이유 |
|----------------|-----------|------|
| 1개 | P 결제 실행 | 중복 승인·금액·최종 상태 등 핵심 정합성 확인 |
| 2개 | P 결제 실행 + O 주문 생성 | 결제 정합성과 연결 수요별 주문 1건 보장 확인 |

실행 전 선택 결과를 기록한다.
두 구간을 선택하면 별도 실행으로 측정하고 배경 트래픽 조건을 기록한다.

### 최소 실행 순서
1. 선택 구간의 입력 상태와 대사 도구를 소수 데이터로 사전 확인.
2. 대상 100건으로 정상 응답 기준 실행 및 전체 대상 대사.
3. 같은 설정으로 300건 또는 1,000건 중 실행 시간에 맞는 한 단계만 확대.
4. P를 선택했다면 작은 대상 집합에 승인 후 응답 유실 조건을 추가하고 복구·중복 승인 대사.
5. 결과와 미검증 범위를 저장한 뒤 다음 선택 구간으로 이동.

P의 Worker 1개·polling 1초에서는 100건 약 2분, 300건 약 5분,
1,000건 약 17분 이상의 처리 시간을 예상한다. 준비·복구·대사 시간은 별도다.
시간이 부족하면 데이터 규모를 줄이고 대상 전체 대사를 유지한다.
부하 확대나 장애 실행을 생략하면 생략 사실을 기록하고 해당 범위의 검증을 주장하지 않는다.
3초 지연과 프로세스 강제 종료는 추가 여유가 있을 때 실행하며 이번 필수 항목은 아니다.

## 시나리오 [O] 주문 생성 부하 테스트

### 목적
공동구매 생성 시 연결된 수요의 주문 생성 처리량과 DB·메모리 사용량을 측정한다.
**공동구매가 생성됐을 때, 연결된 수요마다 주문이 정확히 1건 존재한다**는 기준을 검증한다.

### 대상 API / 실행 진입점
- 현재 공동구매 생성 HTTP API는 없다. GroupBuyController는 조회 API를 제공한다.
- 테스트 전용 내부 진입점 또는 내부 실행기에서 실제 `GroupBuyService.createGroupBuy(productId)` 호출.
- LOAD_TEST_ENABLED=true에서만 진입점이 활성화된다. 내부 API 키와 전용 run 상품을 검증한다.
- POST /api/load-tests/internal/orders/seed: 전용 데이터 및 manifest 생성.
- POST /api/load-tests/internal/orders/{runId}/products/{productId}: 실제 공동구매 생성.
- POST /api/load-tests/internal/orders/verify: manifest 전체를 입력받아 DB 정합성 대사.
- 실행 도구: bash tools/load-test/run-orders.sh (환경변수와 준비 절차는 해당 README 참고).
- Consumer나 `autoCreateOrder()`를 부하 도구에서 직접 호출하지 않는다.

### 시나리오 흐름
```
[Setup — 전용 fixture]
  - 승인된 판매자, AWARDED 상품, 연결 수요와 활성 회원·결제수단 준비
  - 낙찰 직후 상태를 준비하되 낙찰 콜백은 실행하지 않음
  - 판정 예정시각을 주문 측정 종료 이후로 배치
  - 상품별 실행 목록과 예상 수요 ID 목록 저장
      ↓
[Load — 생성 트리거]
  - 상품별 한 번씩 실제 공동구매 생성 서비스 호출
  - 공동구매와 Outbox가 실제 트랜잭션에서 생성
  - Publisher → 주문 Stream → Consumer → 주문 생성
      ↓
[Verify]
  - 주문 커밋 및 메시지 처리 완료 확인
  - 연결 수요별 주문 수와 공동구매 참여 인원 대사
      ↓
[Teardown]
  - 대상 후속 예약과 관계 데이터를 확인하고 manifest 범위만 정리
```

### 측정 지표
| 지표 | 관심사 |
|------|--------|
| 커밋된 신규 주문 수/초 | 실제 주문 처리량 |
| 생성 트리거 응답시간 및 실제 생성 건수 | 입력 처리 지연과 유입 달성 여부 |
| 공동구매 생성 → 주문 완료 시간 | 비동기 완료 지연 |
| 유형별 Outbox 미발행 수·최장 대기 | Redis 발행 이전 적체 |
| Stream group lag / pending | 미전달·처리 중 메시지 |
| Hikari active/pending, DB 락·쿼리 지연 | DB 경합 |
| JVM CPU·heap·GC, DB/Redis 리소스 | 자원 점유 |

공동구매당 이벤트는 1건이다. 이벤트 1건이 주문 수천 건을 생성할 수 있다.
Stream 건수와 주문 처리량을 같은 단위로 해석하지 않는다.

### 필요 데이터
| 항목 | 수량 예시 | 비고 |
|------|-----------|------|
| Member / 활성 BrandPayMethod | 연결 수요 소유자 수에 맞춤 | 회원 상태, 소유 관계 충족 |
| Seller | 1명 이상 | APPROVED, 판매 가능 |
| Catalog / DemandBoard / Product | 공동구매 수에 맞춤 | 전용 데이터, 상품 AWARDED |
| Demand | 100건부터 | 주문 조회 대상 상태, 가격 조건 충족 |
| Manifest | 실행별 1개 | productId, 수요 ID, 기대 주문 수 등 |

**규모 예시**:
- 기준: 공동구매 10개 × 수요 10건 = 주문 100건
- 확대: 100개 × 10건 / 10개 × 100건 = 각각 주문 1,000건
- 총량이 같아도 공동구매별 트랜잭션 크기가 다르므로 별도 실행한다.

### 정합성 기준
- 연결 수요의 주문 누락 0건, 중복 0건, 비연결 수요 주문 생성 0건.
- 공동구매 참여 인원과 실제 반영 대상 주문 수 일치.
- 현재 구현의 탈퇴 회원·가격 초과 등 제외 조건과 ‘연결 수요’ 정의는 사전 확정한다.
- 초기 fixture는 모든 연결 수요가 주문 생성 조건을 만족하게 하며, 사후에 대상을 빼지 않는다.

### 테스트 위치
AWS 동일 VPC의 부하 발생기 및 테스트 전용 내부 진입점.
다른 팀의 낙찰 API나 데이터 준비 완료에 의존하지 않는다.

## 시나리오 [P] 결제 실행 부하 테스트

### 목적
Worker 1개에서 실제 완료 처리량과 리소스 사용량을 측정하고,
부하·외부 응답 지연·재처리 상황에서 중복 승인과 상태 불일치가 없는지 검증한다.

### 대상 API / 실행 진입점
- 준비된 결제 예약에 대해 실제 `PaymentWorkerPool`과 `PaymentWorker` 실행.
- 부하 도구에서 `runOne()`이나 PG 결제 메서드를 직접 호출하지 않는다.
- 배포 설정으로 선택한 앱 내부 가상 결제·승인 조회 구현체를 호출한다.

### 시나리오 흐름
```
[Setup]
  - 실제 앞 단계로 결제 준비·Outbox 발행·Redis 예약 반영 완료
  - 준비 중 Worker 획득 제어, 대상과 최초 예정시각 저장
  - Mock 승인 이력 초기화는 본 실행 대상에 한정
      ↓
[Load]
  - 측정 시작과 함께 Worker 획득 허용 또는 준비된 예약시각 도래
  - claim → 실행 상태 확보 → Mock PG → DB 반영 → 예약 정리
      ↓
[Verify]
  - 주문·결제·수요 상태와 Mock 승인 이력을 건별 대사
  - 대상 처리 및 후속 정리 완료까지 관측
      ↓
[Teardown]
  - 대사 결과와 승인 이력 저장 후 전용 데이터 정리
```

### 측정 지표
| 지표 | 관심사 |
|------|--------|
| DB 결제 성공 완료 수/초 | 실제 결제 처리량 |
| 실패·수동 확인 전환 수/초 | 성공 처리량과 별도 집계 |
| PG 요청·조회·재시도 수와 신규 승인 수 | 재호출과 실제 청구 구분 |
| due 수, DB 처리 중·재시도 대기 수 | 실행 상태별 적체 |
| 최초 예정시각 → 완료 p95/p99/최대 | 사용자 작업 완료 지연 |
| Worker 점유, Hikari active/pending | 외부 대기와 DB 커넥션 영향 |
| JVM·DB·Redis CPU/메모리 | 가상 결제를 포함한 시스템 자원 점유 |
| 유입 종료 → 전체 처리 완료 | backlog 해소 시간 |

ZSET score는 claim과 재시도로 바뀌므로 최초 예정시각을 별도로 보관한다.
ZSET 전체 크기는 순수 대기 건수가 아니며 due=0만으로 완료를 판정하지 않는다.

### 필요 데이터
| 항목 | 수량 예시 | 비고 |
|------|-----------|------|
| 결제 가능한 주문·공동구매 | 결제 대상 수에 맞춤 | 실제 앞 단계로 준비 |
| 준비된 Payments 및 Outbox | 결제 100건부터 | 금액·멱등키·주문번호 등 유효 |
| Redis 결제 예약 | 대상별 실제 반영 | Worker 시작 전 확인 |
| 가상 승인 저장소 | 실행 대상 전체 | 초기 구현은 메모리 가능, 재배포 전 이력 보존 |
| Manifest | 실행별 1개 | 논리적 결제, 기대 금액, 장애 대상 |

### 부하 및 장애 조건
아래 조건을 모두 수행할 필요는 없다. 정상 기준·한 단계 확대·소규모 응답 유실을 우선한다.
지연 및 종료·복구는 선택 확장이다.
| 실행 | 조건 | 기대 결과 |
|------|------|-----------|
| 기준 | 100건, 300ms 정상 응답 | 전건 정상 완료 |
| 확대 | 1,000건 이상, 같은 설정 | 정합성 유지, 처리량·적체 측정 |
| 지연 | 3초 응답 | 지연 영향 측정, 정상 완료 |
| 응답 유실 | 지정 5건은 가상 승인 기록 후 통신 오류에 해당하는 예외 발생 | 조회·복구 후 단일 승인과 DB 일치 |
| 종료·복구 | 승인 이력 영속화가 준비된 경우만 수행 | 미완료 복구, 중복 승인·누락 0건 |

앱 내부 sleep은 실제 HTTP 읽기 타임아웃을 발생시키지 않는다.
응답 유실은 승인 기록 후 실제 클라이언트의 통신 오류 분류에 해당하는 예외를 명시적으로 발생시킨다.
이번 방식은 HTTP 연결·타임아웃이나 실제 PG의 멱등성 보장을 검증하지 않는다.
Worker 1개·polling 1초·Mock 300ms에서는 대략 초당 1건 수준이며,
1,000건 처리에 약 17분 이상 걸릴 수 있다. 완료 기한은 별도로 사전 확정한다.

종료 지점은 별도 실행으로 구분한다:
- Redis claim 후 DB 실행 상태 확보 전
- PG 승인 후 DB 완료 커밋 전
- DB 완료 커밋 후 Redis 정리 전

재현 장치 없이 임의 종료했다면 특정 지점을 검증했다고 표시하지 않는다.
정상 종료 대기 후 재시작은 강제 종료 검증을 대체하지 않는다.
메모리 승인 이력을 사용하는 초기 구현에서는 강제 종료·재시작 검증을 수행하지 않는다.

### 정합성 기준
- 논리적 결제별 실제 중복 승인 0건.
- 금액·주문번호·승인 식별자 오류 0건.
- 완료/복구 기한 이후 PG 이력과 DB 결과 불일치 0건.
- 정상 시나리오의 미완료 0건. 장애 시나리오는 사전에 정한 기대 상태와 일치.

### 테스트 위치
AWS 배포와 앱 내부 가상 결제 구현체. 재배포 및 선택적 종료 검증은 QA와 시간을 조율한다.

## 이번 실행의 검증 한계

- 선택한 1~2개 구간의 입력부터 종료 경계까지만 합격 판정한다.
- 준비 단계에서 앞 구간을 실행했더라도 해당 구간의 부하 성능을 검증한 것은 아니다.
- 다른 팀의 후속 작업이 같은 Worker에 유입되면 실제 배경 작업량으로 기록한다.
- CPU·메모리는 공유 시스템 값이며, 선택 구간만의 점유율이라고 단정하지 않는다.
- 미선택 구간과 미실행 장애 조건은 결과에 '미검증'으로 명시한다.

## 시딩 및 실행 스크립트 뼈대

아래는 구현할 책임과 순서를 설명하는 의사코드이며, 현재 실행 가능한 스크립트가 아니다.
실제 스키마의 필수 컬럼과 상태 조건을 확인한 fixture를 구현하고, 검증 전 완료 행을 만들어 넣지 않는다.

```text
seed(runId, segment):
    전용 회원·결제수단·판매자·상품·수요 준비
    원본 예상 대상 manifest 저장
    if segment == P:
        Worker 획득 제어 상태에서 실제 결제 예약까지 준비 후 입력 검증

run(runId, segment):
    배경 트래픽 및 측정 시작
    O → 중복 없는 상품 목록으로 생성 트리거 실행
    P → Worker 획득 허용 또는 실제 예약 도래
    해당 구간 완료/복구 기한까지 관측

verify(runId, segment):
    manifest 전체를 기준으로 ID별 건수·연결·금액·상태 대사
    실행 이력 및 Mock 승인 이력 대사
    누락/중복/불일치 ID와 미검증 범위 저장

cleanup(runId):
    검증 결과·이력 보존
    대상 작업의 후속 실행 여부 확인
    FK와 실행 의존 순서를 고려해 해당 manifest 소유 데이터만 정리
```

### k6 스크립트 구성 원칙
- 현재 O 스크립트는 shared-iterations로 상품별 한 번씩 생성하는 동시성 기반 burst이다.
- 고정 RPS 검증은 현재 스크립트 범위가 아니며 별도 arrival-rate 설계가 필요하다.
- 미리 만든 고유 상품 목록을 요청별로 한 번씩 배정한다.
- VU별 반복 횟수나 랜덤 선택으로 같은 상품을 중복 생성하지 않는다.
- 요청 실패/응답 유실 시 실제 생성 여부 확인 없이 자동 재호출하지 않는다.
- P는 예약과 실제 Worker가 부하를 만든다. k6에서 내부 메서드 호출을 대체하지 않는다.
- HTTP 성공만으로 업무 완료를 판정하지 않는다. 완료 처리량은 커밋 결과로 집계한다.
- 목표 유입량, 실제 요청량, dropped iterations, 완료 작업량을 별도로 기록한다.

## 앱 내부 가상 결제 구현체 요구사항
- 결제 및 주문번호 승인 조회 인터페이스 구현. 별도 HTTP 서버는 만들지 않는다.
- 기존 결과 반영 로직이 검증하는 필드와 금액·주문번호를 올바르게 반환.
- PG 호출에 해당하는 위치에서 설정된 시간만큼 sleep하며 DB 트랜잭션 바깥의 기존 경로를 유지.
- 멱등키별 승인 결과 유지, 재호출과 신규 승인을 별도 집계.
- 대상 주문번호별 지연 및 승인 기록 후 예외 발생 방식의 응답 유실 주입.
- 메모리 이력 사용 시 대사·결과 보존 후 재배포. 재시작 복구 검증에는 별도 영속화가 필요.
- 장애 조건은 본 실행 대상에만 적용.

## 결과 보고 양식

| 항목 | 기록 내용 |
|------|-----------|
| 식별 | run ID, scenario/segment ID, 앱 버전 |
| 환경 | 인스턴스 수, CPU/메모리, DB/Redis/Hikari 설정 |
| 조건 | Worker 수, polling, Mock 지연·장애 조건 |
| 부하 | 배경 RPS, 구간별 목표·실제 유입량, 대상 수 |
| 경계 | 입력 상태, 측정 종료 지점, 준비 단계 제외 범위 |
| 처리량 | 주문·결제 완료 건수/초 |
| 적체 | 단계별 backlog 최대값, 해소 시간, 완료 지연 |
| 리소스 | CPU·메모리·GC·커넥션 대기·DB 락·Redis 지연 |
| 정합성 | 유형별 위반 수, 실패 ID, 기대값과 실제값 |
| 판정 | 기한 초과, 미검증 항목, 합격/실패 |

총건수만 비교하지 않는다. 한 건 누락과 다른 건 중복이 상쇄될 수 있으므로 건별 대사가 필수이다.
실행 중에도 중복 승인·잘못된 금액·잘못된 상태 전이를 허용하지 않는다.
비동기 처리 중의 일시적 상태 차이는 완료/복구 기한 안에 해소되어야 한다.
